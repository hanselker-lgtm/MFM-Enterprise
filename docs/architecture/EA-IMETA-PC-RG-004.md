## Purpose
Establish the authoritative mandatory-state layer defining the required state that must exist when an applicable mandatory condition is satisfied. The document distinguishes activity from state, defines observable state attributes, evidence, verification, measurement, thresholds, deviation, restoration and review.

## Core Principle
Completion of an activity does not prove that the required state exists. A mandatory condition is satisfied only when its defined required state is demonstrably present within approved boundaries.

```text
MANDATORY CONDITION
        ↓
REQUIRED STATE
        ↓
STATE ATTRIBUTES
        ↓
OBSERVABLE / ASSESSABLE STATE
        ↓
EVIDENCE
        ↓
VERIFICATION
        ↓
PASS / FAIL
```

## Mandatory State Structure

| Element | Required definition |
|---|---|
| Condition | Parent mandatory requirement |
| Required State | State that must exist |
| Baseline | Reference state where applicable |
| Target | Intended compliant state |
| Attributes | Properties defining the state |
| Evidence | Proof that the state exists |
| Verification | Method used to verify state |
| Measurement | Quantitative or qualitative test |
| Threshold | Boundary for conformity |
| Deviation | Permitted or unacceptable departure |
| Restoration | Method to restore required state |
| Review | Reassessment requirements |

## State Definition

The required state shall be stated as an observable condition, not as an intention, activity or plan.

```text
ACTIVITY
  ≠
REQUIRED STATE
  ≠
EVIDENCE OF ACTIVITY
```

## Target State

The target state defines the state required for the applicable mandatory condition to be considered satisfied. It shall be explicit, testable and version controlled.

## Baseline State

Where comparison is necessary, a baseline state shall identify the reference condition against which change or regression is evaluated. Baselines shall be dated and traceable.

## Observable State

Material state shall be observable or objectively assessable. Where direct observation is not possible, an approved proxy, test or assurance mechanism shall be defined.

## State Attributes

State attributes define the properties that determine whether the required state exists. Attributes may include availability, integrity, performance, configuration, authority, security posture, resilience, compliance status, data quality or operational readiness.

## State Evidence

Evidence shall demonstrate the actual state rather than merely demonstrate that a procedure was performed. Evidence shall be attributable, current, relevant, sufficiently complete and protected from inappropriate alteration.

## State Verification

Verification shall test the required state using an approved method and shall be proportionate to materiality.

```text
REQUIRED STATE
      ↓
VERIFICATION METHOD
      ↓
TEST / OBSERVE
      ↓
RESULT
      ↓
PASS / FAIL
```

## State Measurement

Where state is quantitative, measurement shall define source, method, frequency, quality controls, uncertainty and interpretation.

## State Thresholds

Thresholds shall define acceptable boundaries and consequences for warning, deviation, failure and escalation.

```text
STATE VALUE
    ↓
PASS RANGE
    ↓
WARNING / AT-RISK
    ↓
FAILURE RANGE
```

## Security State

Mandatory security state may include required confidentiality, integrity, availability, authentication, authorization, protection, monitoring and incident-response posture.

## Resilience State

Mandatory resilience state may include continuity readiness, recovery capability, restoration capability, dependency resilience, capacity and verified recovery performance.

## Compliance State

Mandatory compliance state shall represent the actual required conformity state, not merely the existence of a policy or completed training.

## Data State

Mandatory data state may include accuracy, completeness, integrity, lineage, timeliness, availability, classification, retention and authorized-use conditions.

## AI and Agent State

AI and agent required state shall include applicable authority, autonomy, policy, safety, tool-access and data-access boundaries.

```text
AI / AGENT
   ↓
REQUIRED GOVERNED STATE
   ↓
WITHIN AUTHORITY?
   ↓
POLICY / SAFETY COMPLIANT?
   ↓
STATE VERIFIED
```

## State Dependencies

Required state may depend on other services, systems, data, people, controls or external conditions. Dependencies shall be identified and their failure effects governed.

## State Deviation

A deviation is a departure from required state. Deviations shall be classified according to materiality and handled according to approved tolerance, escalation and remediation rules.

```text
REQUIRED STATE
      ↓
DEVIATION DETECTED
      ↓
MATERIAL?
 ├── NO  → CORRECT / MONITOR
 └── YES → CONTAIN / ESCALATE / REMEDIATE
```

## State Escalation

Material or systemic deviation shall trigger escalation. Uncertainty about whether the state is materially degraded shall not be silently treated as acceptable.

## State Restoration

Restoration shall return the service, system, process or control to the defined required state and shall be followed by re-verification.

```text
STATE DEVIATION
      ↓
CONTAIN
      ↓
REMEDIATE
      ↓
RESTORE
      ↓
RE-VERIFY
      ↓
RESTORED / NOT RESTORED
```

## State Review and Learning

Required-state definitions shall be reviewed after material regression, repeated deviation, architecture change, risk change, criteria change, regulatory change or evidence that the state no longer represents the intended control objective.

## State Change Control
Changes to a required state shall be governed, approved, versioned and effective-dated. Historical state definitions and determinations shall remain traceable.

```text
CURRENT STATE DEFINITION
        ↓
CHANGE PROPOSAL
        ↓
IMPACT / RISK ASSESSMENT
        ↓
AUTHORITY APPROVAL
        ↓
NEW STATE VERSION
        ↓
EFFECTIVE DATE
```
